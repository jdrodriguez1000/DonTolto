# SPEC — Validación de Env (`f1_1.0`) [v1.3.0-DevilHardened]

> Trazabilidad: Este documento implementa los requerimientos de `docs/f1_1.0/f1_1.0_prd.md`.

## 1. Visión de Arquitectura

El componente central es un script de Python 3.12+ (`check_env.py`) encargado de realizar handshakes con todos los servicios del stack (Supabase, Upstash, Resend, GitHub). Este script actúa como un **Hard-Gate** en el pipeline de despliegue: si una sola validación crítica falla, el proceso se aborta.

### 1.1 Diagrama (texto)
`[GHA Runner / Local]` → `[ARC-05] (check_env.py)` → `[Supabase (TCP/HTTP)]` 
                                         ↳ `[Upstash (REST)]`
                                         ↳ `[Resend (REST)]`
                                         ↳ `[GitHub (REST)]`

### 1.2 Componentes de Arquitectura
| ID | Componente | Responsabilidad | Módulo (`engine/`) |
|---|---|---|---|
| [ARC-05] | Engine Validator | Orquestar checks de red, secretos y permisos. | `engine/src/check_env.py` |
| [ARC-06] | Vault / Secrets | Almacenamiento seguro de credenciales. | `.env` / `GHA Secrets` |
| [ARC-07] | Dependency Manifest | Bloqueo de versiones para reproducibilidad. | `engine/requirements.txt` |

### 3.1 Gestión de Dependencias (Hardened)
Para garantizar la integridad y reproducibilidad absoluta (Zero Drift), el `engine/requirements.txt` debe generarse con **hashes de verificación** (`pip compile --generate-hashes`):
- `httpx==0.27.0` (Cliente HTTP asíncrono).
- `psycopg2-binary==2.9.9` (Driver Postgres).
- `python-dotenv==1.0.1` (Gestión de variables de entorno).
- `pydantic==2.6.4` (Validación de esquemas de datos del reporte).

### 3.2 Estrategia de Resiliencia y Seguridad
#### 3.2.1 Política de Reintentos (Retries)
Toda conexión externa (`Supabase`, `Upstash`, `Resend`, `GitHub`) implementará:
- **Max Retries**: 3 intentos.
- **Backoff**: Exponencial (1s, 2s, 4s).
- **Timeout**: Global de 10s por servicio.

#### 3.2.2 Sanitización de Logs
El script filtrará cualquier substring que contenga las variables de entorno sensibles (`*_KEY`, `*_TOKEN`) antes de emitir el `RunReport` o el `GITHUB_STEP_SUMMARY`. Los errores HTTP se truncarán si contienen headers de autorización.

### 3.3 Lógica Forense Detallada

#### A. `check_pg_extensions`
1. Intentar `CREATE EXTENSION IF NOT EXISTS "uuid-ossp";`, `CREATE EXTENSION IF NOT EXISTS "pg_cron";` y `CREATE EXTENSION IF NOT EXISTS "pg_net";`.
2. Si falla por permisos, verificar si ya existen en `pg_extension`.
3. Validaciones de visibilidad:
    - `SELECT count(*) FROM cron.job;`.
    - `SELECT count(*) FROM net.http_request_queue;` (Verificar esquema `net`).

#### B. Test de Persistencia (Idempotente, Concurrente & DB Hygiene)
Para validar permisos de escritura de forma segura incluso en ejecuciones paralelas:
1. **Name Generation**: El nombre de la tabla temporal será `public._bootstrap_[run_id_short]` (Donde `run_id_short` son los primeros 8 chars del `run_id`).
2. **Setup**: `CREATE TABLE IF NOT EXISTS public._bootstrap_[run_id_short] (id uuid DEFAULT gen_random_uuid(), ts timestamp DEFAULT now());`.
3. **Execute**: `INSERT INTO public._bootstrap_[run_id_short] DEFAULT VALUES;`.
4. **Verify**: `SELECT count(*) FROM public._bootstrap_[run_id_short];`.
5. **Cleanup (Mandatorio)**: `DROP TABLE IF EXISTS public._bootstrap_[run_id_short];`.
6. **Manejo de Errores**:
    - Si el error es `Connection Refused` o `Timeout` (SQLState `08001`, `08006`) → Marcar como `ERROR` de Conectividad (Red).
    - Si el error es `Insufficient Privilege` (SQLState `42501`) en el `CREATE` → Marcar como `WARNING` de Configuración (Permisos), sugiriendo revisión de `search_path` o roles.
7. **Robustez Transaccional**: El `DROP TABLE` debe ejecutarse en una cláusula `finally` para asegurar el cleanup incluso si el `INSERT` falla.

## 6. Decisiones de Diseño y Justificación

- **[ARC-05] usa `httpx`**: Se prefiere por asincronía y manejo avanzado de timeouts. Versión fijada en `requirements.txt` para evitar derivas.
- **Resiliencia ante Red**: Se añade lógica de retries con backoff para evitar falsos negativos en el GHA Runner durante picos de latencia.
- **Higiene de DB**: El test de persistencia usa una tabla efímera `_bootstrap_test` que es eliminada inmediatamente para cumplir con la política de "Zero Footprint" en validación.
- **Sanitización de Logs**: Se implementa un filtro de strings para evitar que secretos aparezcan en logs de CI/CD, priorizando la seguridad sobre el debug detallado en reportes públicos.
- **Validación de ADMIN_UUID**: Se realizará exclusivamente via **Supabase Admin API (HTTP)** o mediante un **RPC (SECURITY DEFINER)** dedicado, evitando el acceso directo de `psycopg2` al esquema `auth` de sistema para prevenir errores de privilegios insuficientes (`SQLState 42501`) falsos. Se mantiene como WARNING si no existe en la DB.
- **GITHUB_STEP_SUMMARY (Reporte Visual)**: El script detectará la presencia de la variable de entorno `GITHUB_STEP_SUMMARY`. Si existe (entorno CI), escribirá el reporte markdown directamente en esa ruta de archivo para visualización en el dashboard de GHA.
    - Columnas: `Service | Check Type | Status | Result/Error`
    - Uso de Emojis: `✅ OK`, `⚠️ WARNING`, `❌ ERROR`.
- **Manejo de Exit Codes**: El script finalizará con `sys.exit(0)` solo si el estado global es `OK` o `WARNING`. Cualquier estado `ERROR` en una validación CRÍTICA (Supabase SQL/HTTP, Env Vars) forzará un `sys.exit(1)` para romper el pipeline.
