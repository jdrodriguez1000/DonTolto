# PRD — Validación de Entorno (`f1_1.0`) [v1.2.0-Devil]

## 1. Resumen Ejecutivo
Esta etapa constituye el **Hard-Gate** de infraestructura. El objetivo es asegurar que el ecosistema (Supabase, Upstash, Resend, GitHub) esté operativamente vinculado y blindado antes de inyectar el DDL de la Fase 1.1. Se desarrolla `engine/src/check_env.py` como una herramienta de diagnóstico forense que valida secretos, conectividad y capacidades de extensiones.

## 2. Objetivos de Negocio
- [OBJ-01] **Cero Errores Silenciosos**: Detectar fallos de configuración de red o permisos antes de iniciar la persistencia de datos.
- [OBJ-02] **Certificación de Extensiones**: Validar que el plan de Supabase permite `pg_cron` y `uuid-ossp` (Pre-requisitos DDL).
- [OBJ-03] **Verificación de Secretos Externos**: Confirmar que los tokens de Resend, Upstash y GitHub son válidos y tienen los scopes necesarios.

## 3. Alcance
### 3.1 En Alcance
- [REQ-01] **Dependency Management Elite**: Uso de `engine/requirements.txt` con hashes de integridad. Librerías: `python-dotenv`, `httpx` (Asincronía preferida sobre `requests`), `psycopg2-binary`.
- [REQ-02] **Validación de Conectividad Dual**: 
    - **HTTP (REST)**: Handshake con PostgREST para asegurar que la API pública responde.
    - **TCP (Direct/Pooler)**: Intento de conexión via SQL para validar que el `service_role` puede consultar el catálogo.
- [REQ-03] **Auditoría de Extensiones (The Big 3)**: Validación de existencia y permisos de ejecución para:
    - `uuid-ossp`: Ejecutar `SELECT uuid_generate_v4()`.
    - `pg_cron`: Consultar `cron.job` para asegurar visibilidad.
    - `pg_net`: Verificar existencia (Requerido por orquestación).
- [REQ-04] **Validación Forense de Env Vars**:
    - Formato Regex para URLs y UUIDs.
    - **Especial**: El `ADMIN_UUID` debe ser validado contra `auth.users` (si la conexión SQL lo permite) o marcando una advertencia si no se puede verificar.
- [REQ-05] **Auth-Matrix (3-Stage Verification)**:
    - **GitHub**: `GET /user` para validar el `GITHUB_TOKEN`.
    - **Resend**: `GET /api-keys` o `POST /emails/test` (Dry-run).
    - **Upstash/Redis**: Validar respuesta del REST API (Ping).
- [REQ-06] **Persistence Test**: Intento de inserción de un log de "Bootstrap" en una tabla temporal (o stdout fallback) con un `run_id` (UUIDv4) generado en runtime.

### 3.2 Fuera de Alcance
- Despliegue de lógica de simulación o scraping.
- Creación de tablas de negocio (Draws, Projections).
- Configuración de DNS o dominios personalizados.

## 6. Métricas de Éxito
- **[MET-01]**: 100% de los servicios críticos (Supabase, Env Vars) en VERDE.
- **[MET-02]**: Latencia de validación total < 8.0 segundos.
- **[MET-03]**: Trazabilidad absoluta: Cada reporte debe incluir el `run_id` persistido o logueado.

## 7. Riesgos y Supuestos (Devil's Advocate)
- **[RSK-01] Plan "Free" de Supabase**: Algunos planes pueden restringir `pg_cron`. **Mitigación**: El script debe alertar específicamente si el error es de permisos de extensión.
- **[RSK-02] Inconsistencia en ADMIN_UUID**: Si el usuario proporciona un UUID que no existe en el proyecto, las RLS fallarán. **Mitigación**: Check preventivo en `auth.users`.
- **[RSK-03] Entorno CI vs Local**: Variables cargadas en `.env` local pueden diferir de GHA Secrets. **Mitigación**: Documentar la obligatoriedad de usar el mismo set de nombres.
