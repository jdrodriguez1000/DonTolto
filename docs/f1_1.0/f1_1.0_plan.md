# PLAN — Validación de Entorno (`f1_1.0`) [v1.3.0-DevilHardened]

> Trazabilidad: Este plan operacionaliza la SPEC `docs/f1_1.0/f1_1.0_spec.md`.

## 1. Estrategia de Entrega (Abogado del Diablo)

Para garantizar un **Hard-Gate** infalible, la implementación no solo debe conectar servicios, sino ser resistente a fallos parciales para ofrecer un diagnóstico completo (Diagnostic-First) antes de abortar el proceso (Fail-Fast-Signal).

### 1.1 Ruta Crítica y Dependencias
1. **Infraestructura Base**: Configuración de `engine/` y `requirements.txt`.
2. **Validación de Secretos**: Lógica de Regex para evitar inyectar basura en los handshakes.
3. **Handshakes Externos (Paralelizables)**: GitHub, Resend, Upstash.
4. **Validación SQL/Persistencia**: Handshake con Supabase y Test de tabla dinámica.
5. **Orquestación de Reporte**: Fusión de estados y salida GHA.

## 2. Desglose de Sprints / Hitos (Blocks)

### Bloque 1: Scaffolding & Setup [Etapa 1.0.1]
- **T-01**: Creación de estructura de directorios: `engine/src/`, `engine/tests/`.
- **T-02**: Definición de `engine/requirements.txt` con hashes de integridad (usando `pip-compile` de `pip-tools`) para fijar `httpx`, `pydantic`, `psycopg2-binary`, `python-dotenv`.
- **T-03**: Generación de `.env.example` blindada con los regex de la SPEC.
- **T-03b**: Módulo de Utilidades: Implementación de helpers para `run_id_short`, formateo de logs y timestamps coherentes.

### Bloque 2: Modelado & Engine Core [Etapa 1.0.2]
- **T-04**: Implementación de esquemas Pydantic (`ServiceResult`, `RunReport`) para garantizar una salida JSON inalterable.
- **T-05**: Lógica de sanitización de logs: decorador o middleware interno para filtrar strings sensibles.
- **T-05b**: Configuración de Criticidad: Mapeo explícito de servicios `CRITICAL` (Supabase, Env) vs `WARNING` (Resend, Upstash).
- **T-05c**: Orquestación Core: Implementación de la función `main` en `engine/src/check_env.py` para coordinar el diagnóstico.
- **T-05d**: Lógica de Agregación: Garantizar que el orchestrator recolecte estados de TODOS los servicios (Diagnostic-First) antes de procesar el exit code final.

### Bloque 3: Handshaking de APIs Externas [Etapa 1.0.3]
- **T-06**: Implementación de `check_github()`: Verificación de tokens y scopes (`workflow`).
- **T-07**: Implementación de `check_resend()`: Handshake de conectividad API.
- **T-08**: Implementación de `check_upstash()`: Ping al REST API de Redis.
- **Nota**: Uso de reintentos con backoff exponencial integrados en cada función.

### Bloque 4: Validación de Database & Persistencia [Etapa 1.0.4]
- **T-09**: Handshake de conectividad dual (SQL via psycopg2 y REST via PostgREST).
- **T-10**: Auditoría de Extensiones: Check de `pg_cron`, `uuid-ossp` y `pg_net`.
- **T-10b**: Robustez de Persistencia: Implementación de limpieza previa (Startup Cleanup) que busque el patrón global de tablas huérfanas `public._bootstrap_*` de corridas anteriores interrumpidas (zombies).
- **T-10c**: Sonda de Capacidades DDL: Implementación de un check explícito de privilegios (`has_schema_privilege` para `CREATE`) para garantizar viabilidad de la Fase 1.1.
- **T-11**: Test de Persistencia Forense: Implementación de la tabla dinámica `_bootstrap_[run_id_short]` con cleanup en bloque `finally`.

### Bloque 5: Integración CI/CD [Etapa 1.0.5]
- **T-12**: Integración de `GITHUB_STEP_SUMMARY`: Generación de tabla markdown para el dashboard.
- **T-12b**: Environment Snapshot: Registro de versión de Python y hashes de `requirements.txt` en el reporte visual para trazabilidad forense.
- **T-13**: Implementación de lógica de Exit Codes: Retornar `1` si hay errores críticos en servicios base.
- **T-14**: Creación de Workflow GHA: Implementación de `.github/workflows/f1_1.0_env_validation.yml` con triggers manuales y programados.
- **T-15**: Checklist de Provisionamiento: Verificación y carga de secretos en GitHub Repo Settings.

## 3. Estrategia de Testing (Verificación)

| Nivel | Método | Objetivo |
|---|---|---|
| **Unit** | Pytest + Mocks | Validar que el parser de reportes maneja latencias extremas y errores HTTP 500. |
| **Integration** | Real Secrets Check | Ejecución manual del script en entorno local con secretos reales para validar conectividad. |
| **Sanity** | GHA Dry-run | Ejecutar el script en un workflow de prueba para validar la inyección en `GITHUB_STEP_SUMMARY`. |
| **Recovery** | Failure Injection | Test de "Falla Controlada": Inyectar secreto inválido adrede para verificar que el pipeline termina con `exit 1` y reporte visual claro. |

---

## 4. Gestión de Riesgos Operativos

| Riesgo | Mitigación |
|---|---|
| **Falsos Negativos (Red)** | Implementación de Max Retries (3) y Timeout global (10s) por servicio. |
| **Fuga de Secretos en Logs** | Sanitización agresiva de URLs y headers en el `ServiceResult`. |
| **Bloqueo por Concurrencia** | El nombre de tabla dinámico basado en `run_id` evita colisiones en ejecuciones paralelas. |
| **ADMIN_UUID Inexistente** | El script emitirá un `WARNING` (No bloqueante) si el UUID es válido en formato pero no existe aún en `auth.users`. |
