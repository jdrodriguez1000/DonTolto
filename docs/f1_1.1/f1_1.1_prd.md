# PRD — Setup de Supabase & DDL (`f1_1.1`) [v1.1.5-Gold]

## 1. Resumen Ejecutivo
Esta etapa constituye la **Cimentación de Datos** del proyecto DonTolto. El objetivo es desplegar el esquema relacional completo en Supabase, implementando la lógica de negocio a nivel de base de datos (Native SQL) para garantizar atomicidad en el cálculo de performance (Backtesting) y blindaje absoluto mediante Row Level Security (RLS). Se establece el modelo de trazabilidad unificada basado en `run_id`.

## 2. Objetivos de Negocio
- [OBJ-04] **Soberanía de Lógica**: Desplazar el cálculo de aciertos (Backtesting) del motor Python a la base de datos para reducir latencia y evitar inconsistencias.
- [OBJ-05] **Integridad Forense**: Asegurar que cada registro de proyección y sorteo esté vinculado a una ejecución traceable (`run_id`).
- [OBJ-06] **Seguridad de Capas**: Implementar un modelo de permisos donde el Motor (GHA) tenga acceso administrativo controlado y la UI (Next.js) esté restringida por RLS.

## 3. Alcance
### 3.1 En Alcance
- [REQ-07] **Esquema Relacional Hardened**: Creación de 7 tablas maestras (`strategies_metadata`, `draws`, `manual_verification_queue`, `projections`, `performance`, `sync_locks`, `system_logs`) con constraints de integridad (CHECK, UNIQUE).
- [REQ-08] **Motor de Scoring Nativo (Async-Stateful)**: Implementación de lógica de cálculo de performance mediante un modelo de **Estado Asíncrono** (worker-ready). 
    - **Mecánica**: El trigger inicial solo marca el estado de la proyección como `pending`. Un servicio en background (`pg_cron` cada 1 min) dispara la función de cálculo por lotes para evitar bloqueos en la tabla `draws`.
    - **Fórmula**: `1pt` por número (máx 5) + `10pts` por superbalota. 
    - **Trazabilidad**: Inserción obligatoria de `processed_at` con precisión de microsegundos en la tabla `performance`.
    - **Regla de Desempate (FIFO)**: En caso de igualdad de score, prevalece la proyección con el `processed_at` más antiguo. Esto incentiva la eficiencia de cálculo y estabilidad del ranking.
- [REQ-09] **Protocolo Double-Entry (Scraper-First)**: 
    - El Scraper (GHA) actúa como la entrada primaria automática.
    - La promoción a `draws` requiere un **Matching Exacto** con una entrada manual (Admin).
    - **Fallback de Continuidad**: Si una entrada de Scraper no recibe su par manual en **24 horas**, el sistema genera un log de nivel `error` en `system_logs` y entra en modo de **Continuidad con Deuda**. El motor usará los últimos rankings autorizados, marcando el performance resultante con `is_verified = false` y `status = 'transient'`.
    - **Protocolo de Recálculo de Deuda**: Si la entrada manual rectifica la del Scraper con posterioridad, la función `fn_verify_and_promote_draw` debe disparar un **Recálculo Atómico** de `performance`, actualizando el estado a `final` e invalidando los registros transitorios anteriores.
    - Si existe discrepancia antes de la promoción, el registro queda bloqueado en `manual_verification_queue` para auditoría y nunca se promociona automáticamente.
- [REQ-10] **Infraestructura de Observabilidad**: Vistas de salud (`v_system_health`, `v_strategy_delta`) y logs atómicos vinculados por `run_id`.
- [REQ-11] **Bulk Ingestion Support**: Función RPC `fn_bulk_insert_projections` optimizada para payloads JSONB. 
    - **Volumen Objetivo (Lean Scale)**: 428 registros por sorteo [(7 Estrategias Analíticas * 30 Juegos) + 2 Real + 2 Única] * 2 Tipos (B/R).
- [REQ-12] **Atomic Locking System**: Tabla `sync_locks` con **TTL de 60 minutos** (Sincronizado con Architecture) e identificación obligatoria por `run_id` (columna persistente en el esquema). Incluir soporte para "Force Unlock" mediante borrado manual del lock por el Admin.
- [REQ-13] **Rotación con Preservación Forense**: Implementación de `pg_cron` para purgado selectivo:
    - Logs de nivel `info` y `debug` > 90 días: Eliminación física.
    - Logs de nivel `error`, `audit` y registros de `manual_verification_queue` (Solo si `is_verified = true` Y **sin conflictos previos**): Archivados o purgados.
    - **Cold Storage Architecture**: Los registros con `is_verified = false` o mismatch detectado son persistidos 180 días. Cumplido el plazo, se mueven a un bucket de Storage. 
    - *Nota de Implementación*: En esta etapa (1.1) solo se define el esquema de la tabla de auditoría y el job de `pg_cron` el cual llamará a un RPC placeholder. La lógica de envío vía Edge Function se implementará en 1.3.
- [REQ-14] **Bootstrap de Infraestructura & Key Management**: 
    - Script de carga inicial para `strategies_metadata`.
    - Creación de tabla `system_configuration` protegida por RLS (solo `service_role` y Admin) para almacenar:
        - `admin_uuid`: Identificador único del administrador para RLS.
        - `debt_threshold_hours`: Tiempo límite antes de entrar en modo Fallback (Default: 24h).
        - `is_system_locked`: Flag global para mantenimientos programados.

## 7. Riesgos y Supuestos (Devil's Advocate)
| ID | Descripción | Probabilidad | Mitigación |
|---|---|---|---|
| [RSK-04] | **Deadlocks en Scoring** | Baja | Procesamiento asíncrono vía `pg_cron` / status worker. |
| [RSK-05] | **Admin Identity Leak** | Baja | Almacenamiento en tabla `system_configuration` con RLS estricto. |
| [RSK-08] | **Matching Ghost** | Baja | Timeout de 48h para entradas huérfanas con cierre forzado y alerta. |
| [RSK-09] | **Overflow de Históricos** | Media | Automatizar purgado a Supabase Storage (Cold Storage) tras 180 días. |
| [RSK-10] | **Deriva de Performance en Fallback** | Media | Implementar `fn_recalculate_performance` ante rectificaciones manuales. |
