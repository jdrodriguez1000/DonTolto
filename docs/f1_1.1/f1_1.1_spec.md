# TECHNICAL SPECIFICATION (SPEC) — Setup de Supabase & DDL (`f1_1.1`) [v1.2.3-Gold]

> Trazabilidad: Este documento implementa los requerimientos de `docs/f1_1.1/f1_1.1_prd.md` y se alinea con `docs/governance/PROJECT_architecture.md`.

## 1. Visión de Arquitectura
La etapa `f1_1.1` establece el núcleo de persistencia y lógica nativa. El sistema utiliza un modelo **Async-Stateful** donde la base de datos no es solo un almacén, sino un motor de cálculo orquestado por `pg_cron`.

### 1.1 Diagrama de Flujo de Datos
`Motor Python (GHA)` → `[ARC-02] projections` (Status: pending) → `[ARC-05] pg_cron` → `fn_compute_async_scoring` → `[ARC-03] performance` (Ranking)

### 1.2 Componentes de Arquitectura
| ID | Componente | Responsabilidad | Módulo (`supabase/`) |
|---|---|---|---|
| [ARC-01] | `Schema DDL` | Definición de tablas, constraints e índices (GIN/B-Tree). | `migrations/` |
| [ARC-02] | `Projections Engine` | Gestión de estados de backtesting (`pending` -> `calculated`). | `fn_compute` |
| [ARC-03] | `Scoring Logic` | Cálculo puntual de aciertos (Overlap `&&`) y puntaje. | `Triggers/RPC` |
| [ARC-04] | `Double-Entry Guard` | Validación y promoción Scraper vs Admin. | `fn_verify` |
| [ARC-05] | `Automation (pg_cron)` | Orquestación de scoring asíncrono y cleanup de logs. | `Extensions` |
| [ARC-06] | `Observability Layer` | Vistas de salud y deltas de performance. | `Views` |

## 4. Lógica SQL (Contratos de Función)

### 4.1 `fn_bulk_insert_projections` (Bulk Ingestion - REQ-11)
*   **Firma**: `fn_bulk_insert_projections(p_run_id UUID, p_payload JSONB)`
*   **Lógica**:
    1.  Itera sobre el JSONB (formato: `[{"strategy": "active_v1", "numbers": [1,2,3,4,5], "sb": 10, "date": "2026-04-09"}, ...]`).
    2.  Valida la existencia de la estrategia/versión en `strategies_metadata`.
    3.  Limpia proyecciones previas para el mismo `run_id` (Idempotencia).
    4.  Realiza un `INSERT INTO projections` masivo filtrando registros inválidos mediante `fn_validate_ball_array`.

### 4.2 `fn_compute_async_scoring` (Scoring Overlap)
*   **Contrato de Cálculo (REQ-08)**:
    ```sql
    -- 1. Contar aciertos numéricos
    hits_count = (SELECT count(*) FROM unnest(p.numbers) n WHERE n = ANY(d.numbers));
    -- 2. Validar Superbalota
    has_sb = (p.superbalota = d.superbalota);
    -- 3. Calcular Score Final (hits + 10 si SB)
    final_score = hits_count + (CASE WHEN has_sb THEN 10 ELSE 0 END);
    ```
*   **Batching & Concurrencia**:
    - Límite de 428 registros por ejecución.
    - **Filtro de Operatividad**: La query de selección DEBE filtrar por `strategies_metadata.is_active = TRUE` mediante un `JOIN`.
    - **Protocolo Anti-Carrera**: Use `UPDATE projections ... WHERE status = 'pending' ... LIMIT 428 FOR UPDATE SKIP LOCKED` para marcar registros como `calculating` antes del scoring.
*   **Garantía FIFO (Precision)**: Para evitar colisiones en bulk inserts, el campo `processed_at` se inyectará mediante:
    `clock_timestamp() + (row_number() OVER () * interval '1 microsecond')`.


### 4.3 `fn_verify_and_promote_draw` (Double-Entry)
1.  **Detección de Coincidencia**: Se comparan entradas en `manual_verification_queue` con el mismo `draw_date` y `type`.
    - `scraper_entry` vs `admin_entry` (Priorizando el registro Admin más reciente: `ORDER BY created_at DESC LIMIT 1`).
    - Si `(scraper.numbers = admin.numbers) AND (scraper.superbalota = admin.superbalota)` -> Match Exitoso.
    - Si existe diferencia tras la entrada del Admin -> `is_conflict = TRUE` y queda bloqueado. Se requiere intervención manual o nueva entrada Admin corregida.
2.  **Promoción**: Si hay par idéntico -> Mueve a `draws` (Status: `final`, `is_manual=TRUE`). Los registros sobrantes en la cola para esa fecha/tipo se marcan como `is_verified = TRUE` para limpieza.
3.  **Fallback**: Si pasadas 24h (Config) solo existe `entry_source='scraper'` -> Mueve a `draws` (Status: `transient`), activa Recalculo y loguea `error`.
4.  **Recálculo Atómico y Trazabilidad Forense**: Si una rectificación manual contradice un estado `transient`: 
    - **Backup de Auditoría**: Antes de borrar, insertar en `system_logs` (level: `audit`) el estado previo de los registros de `performance` eliminados en formato JSONB dentro del campo `metadata`.
    - Elimina registros en `performance` vinculados al `draw_id` anterior (identificado por fecha/tipo).
    - Resetea `projections.status = 'pending'` para las proyecciones de esa fecha/tipo.
    - Promueve el nuevo registro manual a `draws` como `status = 'final'`.
    - El nuevo `draw_id` será procesado por el siguiente ciclo del Job de Scoring.

### 4.4 `fn_manage_lock` & `fn_monitor_and_activate_fallback`
*   **fn_manage_lock**: 
    - **Validación de Stale Lock**: Antes de adquirir, verifica si existe un lock vigente (`expires_at > now()`).
    - Si existe y tiene un `run_id` distinto -> Error (Process Locked).
    - Si ha expirado o el `run_id` coincide -> Actualiza `acquired_at` y setea `expires_at = now() + interval '60 minutes'`.
*   **fn_monitor_and_activate_fallback**:
    - Busca registros en `manual_verification_queue` con `created_at < now() - (SELECT debt_threshold_hours FROM system_configuration LIMIT 1) * interval '1 hour'` y `is_verified = false`.
    - Por cada hallazgo: Invoca `fn_verify_and_promote_draw` forzando `status = 'transient'`.

### 4.5 `fn_cleanup_logs` (Mantenimiento Forense - REQ-13)
*   **Lógica de Purgado**:
    - `DELETE FROM system_logs WHERE level IN ('info', 'debug') AND created_at < now() - interval '90 days'`.
    - `UPDATE system_logs SET is_archived = TRUE WHERE is_archived = FALSE AND created_at < now() - interval '180 days'`.
    - **Mantenimiento de Cola**: `DELETE FROM manual_verification_queue WHERE is_verified = TRUE AND is_conflict = FALSE AND created_at < now() - interval '180 days'`.
    - *Nota*: Los registros marcados con `is_archived` o eliminados físicamente se consideran candidatos para Cold Storage (Stage 1.3). Por ahora, el job de `pg_cron` llamará a un RPC que envuelve esta lógica.

### 4.6 `fn_validate_ball_array` (Integridad de Datos)
*   **Contrato de Validación**:
    - Recibe `ball_array INTEGER[]`.
    - **Reglas de Oro**: 
        1. Cardinalidad exacta = 5.
        2. Valores entre 1 y 43 sin duplicados.
        3. El array DEBE estar ordenado ascendentemente.
    - Retorna `BOOLEAN` o dispara `EXCEPTION` si falla, garantizando que el índice GIN sea eficiente.

### 4.7 `fn_setup_security_context` (RLS Bootstrap)
*   **Mecánica**: 
    - Al inicio de cada sesión administrativa, se ejecuta `SELECT fn_setup_security_context()`.
    - **Seguridad**: Definida como `SECURITY DEFINER` y propiedad de `postgres` para permitir el acceso a `system_configuration` y la ejecución de `set_config` en entornos restringidos.
    - Obtiene `admin_uuid` de `system_configuration`.
    - Ejecuta `PERFORM set_config('app.current_admin_id', admin_uuid::text, true)`.
    - Las políticas RLS referenciarán `current_setting('app.current_admin_id')` para evitar subqueries recursivas en cada fila.

## 7. Diseño de Seguridad (RLS Hardened)
*   **Mapeo de Roles de Negocio**:
    - **Admin**: Todo usuario con el role `authenticated` cuyo `auth.uid()` coincida con el `admin_uuid` de `system_configuration`.
    - **Service**: El role `service_role` heredado de Supabase.
*   **Políticas Mandatorias**:
    - `system_configuration`: `SELECT` para todos; `UPDATE` restringido a `service_role`.
    - `draws` / `performance` / `projections`: `SELECT` para Admin y Service; `web_anon` denegado.
    - `system_logs`: `INSERT` permitido para Service; `SELECT/DELETE` restringido a Admin.
    - **Principio de Mínimo Privilegio**: La cuenta `service_role` (GHA) solo tiene acceso a `INSERT/UPDATE` en `projections` y `manual_verification_queue`. No puede borrar logs de auditoría.
