# Plan de Implementación — Setup de Supabase & DDL (`f1_1.1`)

> Trazabilidad: Este plan ejecuta `docs/f1_1.1/f1_1.1_prd.md` según el diseño de `docs/f1_1.1/f1_1.1_spec.md`.

## 1. Resumen del Plan
El objetivo de esta etapa es establecer el cimiento de persistencia y lógica procedimental en Supabase (PostgreSQL). La estrategia se centra en un despliegue incremental "Bottom-Up", comenzando por la infraestructura de configuración (Singleton), escalando a la integridad referencial y finalizando con los motores de cálculo asíncronos (Scoring) y observabilidad.

**Hitos Clave:**
- **M0**: Validación de infraestructura y extensiones Supabase aprobada.
- **M1**: Esquema relacional blindado con constraints de integridad (Hardened DDL) y registro Singleton configurado.
- **M2**: Motores RPC operativos con lógica de desempate y recálculo atómico testeada individualmente.
- **M3**: Suite de tests de integración SQL validando el 100% de los contratos de la SPEC con integración continua verificada.
- **M4**: Ciclo de desarrollo TDD (Red-Green-Refactor) completado para lógica procedimental.
- **M5**: Estrategia de migraciones granulares (1 script por bloque) validada para trazabilidad técnica.

## 2. Metodología de Ejecución (Pilar Técnico)
Para esta etapa, se impone el uso de **TDD (Test-Driven Development)** en el desarrollo de funciones RPC y lógica de base de datos compleja:
1.  **RED**: Definición de la suite de pruebas unitarias SQL (vía scripts de test) que validen los requerimientos de la SPEC y fallen inicialmente.
2.  **GREEN**: Implementación de la lógica mínima necesaria en PostgreSQL para que las pruebas pasen satisfactoriamente.
3.  **REFACTOR**: Optimización de la lógica (índices, legibilidad, performance) manteniendo el estado verde de las pruebas.

## 3. Backlog de Trabajo (WBS)

### B0 — Validación de Entorno (Pre-vuelo)
- **Objetivo**: Garantizar que el tenant de Supabase soporta los requerimientos técnicos de la SPEC y el runner de pruebas.
- **Entregables**: 
  - Script de validación de extensiones (`pg_cron`, `pg_net`, `pgtap`).
  - Reporte de compatibilidad de versión de Postgres (>= 15.0).
  - Validation Check: Verificación de `search_path` por defecto para prevenir ataques de secuestro de esquemas.
  - **Confirmación de Contrato**: Validación de disponibilidad de funciones `IMMUTABLE` para constraints de B2.
- **Duración estimada**: 0.3 días
- **Hito de aceptación**:
  - [ ] **Contexto de Operación**: Confirmada disponibilidad de `pg_cron` y el runner `pgtap`.
  - [ ] **Data Security**: Suite de tests `pgtap` validando que el `search_path` de las funciones críticas está restringido a esquemas autorizados.

### B1 — Infraestructura Base & Configuración (Seed)
- **Objetivo**: Habilitar contrato Singleton y sembrar la configuración administrativa.
- **Componentes [ARC] relacionados**: [ARC-01], [ARC-05]
- **Requerimientos que implementa**: [OBJ-05], [REQ-14]
- **Entregables**: 
  - Tabla `system_configuration` con `CHECK(id=1)`.
  - **Script de Siembra (`supabase/seed.sql`)**: Inyección del `admin_uuid` administrativo para entornos locales/CI.
  - Inserción de `debt_threshold_hours` (24h) y `is_system_locked` (false).
  - Tabla `system_logs` para observabilidad con política de retención configurable (B6).
  - **Integridad del Singleton**: Trigger `tg_prevent_singleton_delete` para impedir el borrado accidental del registro de configuración.
  - Función `fn_validate_ball_array` (**STABLE** - Desacoplada de caché rígida).
- **Duración estimada**: 0.3 días
- **Dependencias**: B0
- **Hito de aceptación**:
  - [ ] **Inyección de Secretos**: El UUID administrativo en `system_configuration` se obtiene mediante la variable de entorno `SUPABASE_ADMIN_UUID` (inyectada en `seed.sql` vía CLI o Vault).
  - [ ] Función `fn_validate_ball_array` retorna `true` con inputs válidos.

### B2 — Esquema de Datos Transaccional
- **Objetivo**: Crear tablas core para resultados y validación de entrada manual.
- **Componentes [ARC] relacionados**: [ARC-01]
- **Requerimientos que implementa**: [OBJ-05], [REQ-07]
- **Entregables**: 
  - Tablas: `draws`, `manual_verification_queue`.
  - Índice `idx_draws_date_type` (Unique B-Tree).
  - Constraints `NOT NULL` y validadores de integridad (Numbers array check).
- **Duración estimada**: 1.0 días
- **Dependencias**: B1
- **Hito de aceptación**:
  - [ ] Inserción de datos con arrays mal formateados o desordenados es rechazada.
  - [ ] **Integration Check 1**: Intento de duplicar `(draw_date, type)` en `draws` es bloqueado por el índice único.

### B3 — Motor de Performance & Proyecciones
- **Objetivo**: Implementar el esquema de predicciones, performance y lógica de ingesta masiva.
- **Componentes [ARC] relacionados**: [ARC-02], [ARC-03]
- **Requerimientos que implementa**: [OBJ-04], [REQ-11]
- **Entregables**: 
  - Tablas: `strategies_metadata`, `projections`, `performance`.
  - **Esquema de Concurrencia**: Inclusión de `last_heartbeat` y `worker_id` en la tabla `projections` para trazabilidad de procesos asíncronos distribuidos.
  - Función `fn_bulk_insert_projections` (Manejo de JSONB masivo con **Chunking mandatorio de 1000 recs/batch**).
  - **Unit Test SQL**: Prueba de validación de ingesta masiva e idempotencia de proyecciones.
  - Índice GIN `idx_projections_numbers` en `projections.numbers`.
  - Índice compuesto `idx_performance_tiebreak` en `performance`.
- **Duración estimada**: 1.0 días
- **Dependencias**: B2
- **Hito de aceptación**:
  - [ ] **Garantía de Estabilidad**: Ingesta masiva vía `fn_bulk_insert_projections` procesa 100+ registros exitosamente. La función implementa el particionamiento (1000 recs/batch) internamente mediante bucles PL/pgSQL para proteger la memoria de la sesión.
  - [ ] Estructura de columna generada `score` validada en el esquema de la tabla `performance`.

### B4 — Capa de Seguridad & Contexto
- **Objetivo**: Blindar el acceso comercial y técnico mediante RLS y gestión de roles.
- **Componentes [ARC] relacionados**: [ARC-04]
- **Requerimientos que implementa**: [OBJ-06]
- **Entregables**: 
  - `fn_setup_security_context` (**SECURITY DEFINER**, **Hardened search_path**) para inyección de `app.current_admin_id`.
  - Configuración de `pg_cron` (GRANT usage on SCHEMA cron to service_role).
  - **Estrategia Fail-Closed**: Políticas RLS unificadas con cláusulas `COALESCE` mandatorias (ej. `COALESCE(current_setting('app.id', true), '00...0')`) para denegar acceso ante falta de contexto.
- **Duración estimada**: 1.0 días
- **Dependencias**: B3
- **Hito de aceptación**:
  - [ ] **Matriz de Roles Validada**: Test de acceso para 4 roles (Anon, Auth, Admin, Service).
  - [ ] Usuario `web_anon` recibe 0 filas en todas las tablas transaccionales.
  - [ ] **Integration Check 2**: El rol administrativo accede mediante `fn_setup_security_context` y visualiza datos restringidos.

### B5a — Motores RPC (Business Logic)
- **Objetivo**: Implementar la inteligencia procedimental y la lógica de recálculo atómico.
- **Componentes [ARC] relacionados**: [ARC-03], [ARC-04]
- **Requerimientos que implementa**: [OBJ-04], [REQ-08], [REQ-09]
- **Entregables**: 
  - Función `fn_compute_async_scoring` (**SECURITY DEFINER**, **Hardened search_path**, Batch 428, **SKIP LOCKED**).
  - Función `fn_verify_and_promote_draw` (**SECURITY DEFINER**, **Hardened search_path**, Atomic Recalculate).
  - **Snapshotting de Parámetros**: Todas las funciones RPC deben capturar constantes de `system_configuration` en variables locales al inicio de la transacción para evitar inconsistencias por cambios *mid-flight*.
  - Protocolo Matching Ghost (Lógica de atomididad para entradas > 24h).
  - **Manejo de Transacciones**: Implementación de `SAVEPOINT` y bloques `EXCEPTION` exhaustivos.
  - **Backup de Auditoría**: Implementación forense que guarda el estado previo de `performance` en `system_logs.metadata` antes de la limpieza de recálculo.
  - **Unit Tests SQL**: Cobertura de tests para casos de éxito, rectificación y falla parcial (ADR-04).
- **Duración estimada**: 3.5 días (Ajustado por complejidad de Recálculo y TDD)
- **Dependencias**: B4
- **Hito de aceptación**:
  - [ ] Rectificación manual dispara limpieza de performance, backup en logs y reset de status a 'pending' (ADR-04).
  - [ ] Función de promoción resuelve conflictos Admin vs Scraper prioritizando Admin (`ORDER BY created_at DESC`).
  - [ ] **Garantía Anti-Carrera**: Validación de que `fn_compute_async_scoring` no procesa registros bloqueados por otros workers.

### B5b — Automatización & Orquestación
- **Objetivo**: Configurar cronjobs y gestión de concurrencia.
- **Componentes [ARC] relacionados**: [ARC-05]
- **Requerimientos que implementa**: [REQ-09], [REQ-12]
- **Entregables**: 
  - Tabla `sync_locks` (Esquema Hardened: `lock_key`, `run_id`, `acquired_at`, `expires_at`).
  - Función `fn_manage_lock` (Validación de Stale Locks y gestión de TTL 60m).
  - Función `fn_monitor_and_activate_fallback` (Activación modo Fallback > 24h).
  - Configuración de `pg_cron`: Scoring (1 min), Fallback (1 hora), Cleanup (5 min).
  - **Lógica de Resiliencia (Anti-Poison Pill)**: Actualización de `projections` para incluir `retry_count` y manejo de estado `error_fatal`.
- **Duración estimada**: 1.0 días
- **Dependencias**: B5a
- **Hito de aceptación**:
  - [ ] **Garantía Anti-Bloqueo**: La función de orquestación establece un `SET LOCAL statement_timeout = '55min'` para asegurar la liberación del lock antes de su expiración por TTL (60m).
  - [ ] **Mecanismo de Recovery Determinista**: Función `fn_recover_stalled_projections` solo resetea registros si `last_heartbeat` es anterior a 30 min, mitigando conflictos con workers lentos (zombies).
  - [ ] Job de `pg_cron` invocado manualmente procesa proyecciones pendientes.

### B6 — Observabilidad & Mantenimiento
- **Objetivo**: Desplegar vistas de reporte, mantenimiento forense y validación final.
- **Componentes [ARC] relacionados**: [ARC-06]
- **Requerimientos que implementa**: [OBJ-05], [REQ-10], [REQ-13]
- **Entregables**: 
  - Vistas `v_system_health` y `v_strategy_delta`.
  - Función `fn_cleanup_logs` y su programación en `pg_cron`.
  - **Data Prep Script**: Generación de 428 registros sintéticos para validación de carga.
  - Script de test de integración `tests/database/integration_f1_1.1.sql`.
- **Duración estimada**: 1.0 días
- **Dependencias**: B5b
- **Hito de aceptación**:
  - [ ] **Prueba de Estrés [MET-05]**: Procesamiento asíncrono de 400+ registros en < 500ms validado en logs.
  - [ ] Ejecución exitosa de la suite de integración simulando flujo completo.
  - [ ] `fn_cleanup_logs` purga registros `info` según la retención definida.

## 5. Estrategia de Pruebas (Ciclo TDD)
| Nivel | Enfoque | Herramienta | Requisito de Salida | Bloque |
|---|---|---|---|---|
| **Unitarias (Red)** | Lógica de funciones e integridad | pgTap / SQL Unit Scripts | El test debe fallar ante lógica inexistente o incorrecta | B5a |
| **Funcionales (Green)** | Contratos de la SPEC | `SQL Check Commands` | Violaciones de integridad y lógica de negocio pasan tests unitarios | B5a/B5b |
| **Integración (Refactor)** | Flujo Scoring -> Draws | Supabase CLI (Local Env) | Flujo end-to-end verificado en Docker con performance optimizada | B6 |
